# ★★ 2026-09-29 晚 修订（**§1 作废重写**）—— 用户给了验收标准

## 用户给的验收标准（**这是全篇最要紧的一句**）

> **"期望的效果是：touch 往前摆的时候，机械臂末端也往 Y 轴正方向摆动。"**

⇒ **这是【基座系】的说法**（"往 +Y 摆" = 绕基座 +X 正转），不是"绕末端自身轴"。
⇒ **而 §1 写的 `R_new = R_ref·(C·ΔR·Cᵀ)` 是右乘 = 在【末端自身系】里转。形状不对。**

## 为什么不能一律用基座系：**会坏掉自转**

器件自转 θ ⇒ 变成"绕基座某固定轴转 θ"。标定姿态上它恰好 ≈ 末端自身轴（所以今天能用）；
**一旦非正位，自转就变成"把末端掰一下"而不是"拧一下"** ⇒ J6 不再是纯自转。

⇒ **正确形状是【混合】的**：**摆动锁在基座系，自转绕末端自身轴。**

## 重写后的 §1（**取代原 §1**）

```
① ΔR_d = R_refStylusᵀ · R_curStylus         （器件系增量，已有）
② rv    = rotvec(ΔR_d)                       （度）；拆成「摆动」两分量 + 「自转」一分量
③ 摆动: ω_base = M · rv_摆动                  （M = 常 3×3：器件三轴 → 基座三轴）
        R_tilt = exp([ω_base]×) · R_ref       ← 左乘 = 往基座 +Y 摆 ✓
④ 自转: R_new  = R_tilt · Rz(s6 · rv_自转)    ← 右乘 = 绕【新的】末端自身轴拧 ✓
```

**§2（用 `Jw⁻¹` 解 J4/J5/J6）一字不改** —— 它吃的是"目标朝向"，与目标怎么来无关。

> ★ **自转已确认（用户 2026-09-29）**：**"自转直接沿用现在的 J6 转动的方案即可"**
> ⇒ 上面第 ④ 步的"右乘绕末端自身轴"就是要保留的语义，**不要**把自转也锁到基座系。
> 这也意味着 **`BTN2_J6_SIGN` 那一路的实测结论（−1）继续有效**，不必重新标。

## ★★ `M` 收敛成【一个参数】：`M = Rx(φ)`

用户给的验收标准是 **"touch 往前摆 ⇒ 机械臂末端往 Y 轴正方向摆动"**。
"往 +Y 摆"（末端轴指向下时）**= 绕基座 +X 正转**。而"往前摆"是**器件 X 轴**（实测：
前后摆 ≈ (+1.00, +0.08, +0.04) 器件系）⇒

```
    M · ê_x = ê_X        （器件 X  →  基座 X）
```

`M` 还要满足"**同样的摆动角度 ⇒ 同样的转动角度**"（否则手感会被悄悄缩放）
⇒ `M` 应当是**旋转**。**固定 ê_X 的所有旋转 = 绕 X 转的那一族** ⇒

```
    ★  M = Rx(φ)      ← ★★ 只有一个待标定量 φ ★★
```

于是器件三轴的像全部确定：

| 器件轴 | 物理动作 | 经 `M` 映到基座 | 去哪 |
|---|---|---|---|
| X | 前后摆 ≈ (+1.00,+0.08,+0.04) | **ê_X** | 摆动（左乘） |
| Y | 左右摆 ≈ (+0.16,+0.98,+0.08) | (0, cos φ, sin φ) | 摆动（左乘） |
| Z | 自转 ≈ (+0.10,−0.01,+0.99) | (0, −sin φ, cos φ) | **不走 M**，走第 ④ 步的右乘 |

**⇒ 整个标定只剩一个数 φ**，而且它的意义可以当场问清楚、当场调：

> **φ 由「器件左右摆时，末端应该往基座的哪个方向摆」唯一确定。**
> φ = 0 ⇒ 器件左右摆映射到**绕基座 Y 转**；φ = ±90° ⇒ 映射到**绕基座 Z 转**。

⚠ **这一步需要操作员回答**（本文件不替用户定）：
**器件左右摆时，你期望末端往基座哪个方向摆？**（前/后 = ±Z？还是别的？）
—— 这条定不下来，φ 就没有判据。

### ★★ 操作员已答（2026-09-29）：**φ = 0 ⇒ `M = I`**

> **"往左摆时机械臂朝 X 轴负方向摆动。"**

**推导（几何核过）**：末端轴朝下 = 基座 −Z 时，

| 要求 | 末端轴要往哪摆 | 对应的基座旋转 |
|---|---|---|
| 前摆 ⇒ 往 **+Y** 摆 | tip → +Y | `Rx(θ)`：`Rx(θ)·(0,0,−1) = (0, sinθ, −cosθ)` ✓ |
| 左摆 ⇒ 往 **−X** 摆 | tip → −X | `Ry(θ)`：`Ry(θ)·(0,0,−1) = (−sinθ, 0, −cosθ)` ✓ |

⇒ 器件 X → 基座 X、器件 Y → 基座 Y ⇒ `M·ê_x = ê_X` ∧ `M·ê_y = ê_Y`
⇒ **`M = I`（φ = 0）**。

**⇒ 摆动那一半的映射就是「器件轴 = 基座轴」，没有待标定参数。**

### ⚠ 但**符号**仍要上机核（这与 φ 是两件事）

`M = I` 定的是**哪根轴对哪根轴**；**正负**是**器件侧的约定**（"往前摆"到底是 `+rv_x` 还是 `−rv_x`），
**推不出来，只能看**。⇒ 与当年拧 `BTN2_J*_SIGN` 同一类，但**从三个数减到两个**
（摆动两轴；自转那一路的符号已有实测结论 `−1`，见 `BTN2_J6_SIGN`）。

**折进 `M` 的写法**：`M = Rx(φ) · diag(sx, sy, 1)`，`sx, sy ∈ {+1,−1}`。
⇒ 待定 = **φ（已定 = 0）+ 两个符号**；默认取 `(sx, sy) = (−1, −1)`（沿用今天 `BTN2_J4/J5_SIGN` 的实测值），
**上机看方向、不对就翻**。

### φ 怎么调（上机，一次就够）

`Config` 加一个 `BTN2_TILT_PHI_DEG`（默认 0）+ 一行 `M = Rx(φ)`；
**用两个键微调 φ（±5°）**，操作员边按边看"左右摆对不对"，对了就停。
**回滚 = 一个常数。** 与 `BTN2_J*_SIGN` 当年"现场拧三个符号"是同一套做法，只是**从三个数降到一个数**。

## ★ 为什么原 §1 必须作废：`[z4 z5 z6]` 根本不是旋转矩阵

设计原写 `C₀ = R_ref(P₀)ᵀ·[z4 z5 z6](P₀)·diag(s)`，并要求 `det(C₀) = +1`。
2026-09-29 用探针 `tests/_det_c0_probe.cpp`（只读，调 `Kinematics::jacobian`）实测：

```
J5 =   0°   det =  0.000000   |z4·z6| = 1.0000   ← 退化
J5 =  90°   det = −1.000000   |z4·z6| = 0.0000
J5 =  45°   det = −0.707107   |z4·z6| = 0.7071   ← = |cos J5|
J5 = −45°   det = +0.707107   |z4·z6| = 0.7071
J5 = 179°   det = −0.017452   |z4·z6| = 0.9998   ← = sin(179°)
J5 = 180°   det =  0.000000   |z4·z6| = 1.0000   ← 退化
J5 = −70°   det = +0.939693   |z4·z6| = 0.3420   ← = |cos 70°|
```

**⇒ `det([z4 z5 z6]) = −sin(J5)`，且 `z4·z6 = ±cos(J5)`**（200000 个位姿的扫描：符号约 50/50）。

**⇒ `[z4 z5 z6]` 只在 `J5 = ±90°` 时才是旋转矩阵。**

**⇒ 于是原 §1 的两个要求在数学上不相容**：
> "在 P₀ 上逐位退化回旧实现" ⇒ 唯一解 `C = R_refᵀ·[z4z5z6]·diag(s)`；
> "`C` 必须是旋转" ⇒ 需要 `[z4z5z6]` 是旋转。**只有 `J5(P₀) = ±90°` 时两者才相容。**

**⇒ 用户 2026-09-29 选【甲】：放弃"逐位退化"，`M` 按物理安装定义、上机重新标定。**
（原文那句"标定姿态上手感逐位不变"的承诺**作废**；操作员已标过两次符号，第三次不贵。）

- **`z6` 恒为末端自己的接近轴** ⇒ J6 永远等价于"自转" ⇒ **这就是"自转没问题"的原因**，

## 1. 目标朝向怎么算

```
R_ref  = 按下时 FK 的末端姿态        ← Kinematics::composeTransform(m_jointRef) 的旋转部分
ΔR_d   = R_refStylus^T · R_curStylus （已有，器件系增量）
R_new  = R_ref · (C · ΔR_d · C^T)    ← 唯一的公式改动
```

`C` = "器件三轴 ↔ 末端三轴"的固定对应，是**新引入的标定常数**；今天那三个
`Config::BTN2_J*_SIGN`（`Config.h:980/984/985`）就是它的劣化版。

### `C` 不用重新标定就能定出来 —— 本方案最要紧的一点

取标定姿态 P₀，用现成 `Kinematics::jacobian` 拿 J4/J5/J6 的转轴 `z4,z5,z6`（基座系）：

```
C₀ = R_ref(P₀)^T · [z4 z5 z6](P₀) · diag(s4, s5, s6)      // s = 今天那三个 SIGN
```

### 为什么它是"退化"而不是"换一套手感"

J1/J2/J3 冻结 ⇒ `Jw = [z4 z5 z6]` ⇒ 由 `ω = Jw·ΔJ` 反解：

| 器件绕 | 今天的代码 | 新公式在 P₀ 上 |
|---|---|---|
| 器件 X（前后摆） | 绕 `z4` 转 `s4·rv_x` | 绕 `z4` 转 `s4·rv_x` ✓ |
| 器件 Y（左右摆） | 绕 `z5` 转 `s5·rv_y` | 绕 `z5` 转 `s5·rv_y` ✓ |
| 器件 Z（自转） | 绕 `z6` 转 `s6·rv_z` | 绕 `z6` 转 `s6·rv_z` ✓ |

⇒ ★ **"在 P₀ 上新实现与旧实现逐位相等"是一条可断言的回归判据**，操作员已认可的手感
一个字节都不用重谈。离开 P₀ 后公式给出 `R_ref(当前)·C₀·rv`，即"我在世界里怎么拧笔，
机械臂的笔就怎么拧" —— 正是今天缺的那样。

自转仍是纯 J6：`C₀·e_z = R_ref^T·z6·s6` ⇒ 绕 `z6` 转。

### ⚠ 两条必须实测、不许假设的

1. **`det(C₀)` 必须 = +1**，否则它不是旋转、整个公式作废。
   现在的三个 `−1` 的 `det = −1`；而 `det(C₀) = det([z4 z5 z6])·(−1)`
   ⇒ **恰好当肘腕三轴是左手系时两种 `−1` 相互抵消、`C₀` 合法**。
   这是一次**纯离线 FK 计算**（给定 P₀ 就能算），放在实现的**第一步**做。
   算出来是 `−1` ⇒ 是一条真发现，回来重谈。
2. **P₀ 的关节角要有出处**。候选：09-24 那次符号实测按下时的 `J|`（现场日志里录过）；
   取不到就约定一个"正位"姿态并由操作员复现一次。**不许凭记忆写一组关节角。**

## 2. 怎么解 J4/J5/J6

J1/J2/J3 冻结 ⇒ 3 自由度 ⇒ 3×3 牛顿迭代（复用现成件，不赌腕部几何）：

```
q ← ref[3..5]
重复 ≤ 5 次:
    Jw  ← Kinematics::jacobian([ref0..ref2, q]) 的第 3~5 行、第 3~5 列
    v   ← rotvec( R_new · FK_R([ref0..ref2, q])^T )      // 世界系误差（度）
    dq  ← Jw^T (Jw·Jw^T + λ²I)^-1 v                      // 阻尼；λ 自适应，同 Kinematics::inverse
    q  += dq
    |v| < tol ⇒ 收敛
自验: |rotvec(R_new · FK_R(最终 q)^T)| < tol，否则【拒绝：本帧不下发 + 一次性出声】
```

- **不赌球腕**：用 FK 回代而不是闭式欧拉分解。腕部几何（`J4_X/J4_Z/J5_Y/J6_Y`）将来改了不用重推。
- **阻尼是必须的**：肘腕接近展开时 `Jw` 退化，无阻尼会给出巨大 ΔJ。
- **线性化误差由迭代消掉**，不靠"2~3 次够不够"的猜。
- **自验那道门**与现有"FK 位置门"同款形状；报一次性消息复用
  `m_btn2JointRefRejectLogged` 那套（`RelayCore.cpp:1585`，复位点在 `onButton2Press`）。
- 退化分支：`v ≈ 0` 直接收敛；`Jw` 的 |det| 低于门限 ⇒ 直接拒绝，不迭代。

现成件：`Kinematics::composeTransform`（`Kinematics.cpp:96`）· `Kinematics::jacobian`
（`Kinematics.cpp:208`，行 0~2 线性、行 3~5 角速度）· `solveLinear6` 的自适应阻尼写法
（`Kinematics.cpp:397-451`）。

θ > 150° 就把 `R_new` 按 `150/θ` 缩回同一个轴上（**方向不变、幅度受限**）。
逐关节夹会破坏方向（解出来的一根向量被夹歪了，末端就朝错的方向走）。
`clampJointStep` 的逐轴限幅仍在下一层照旧（它只影响过渡帧，最终仍收敛到精确目标）。

### ★★ 单次调用的**能力上界 = 180°**（= 入口能造出的最大目标）—— 但它**不等于**"必然解得出"

★ 2026-09-29 实施后补记（此前这条**只活在实现计划与提交信息里**，本文档没有）：
上面表里那个 `ORIENT_MAX_OFFSET_DEG`（150°）是**目标侧**的限幅，**不是**解算能力。
两者的关系在 Task 7 之前**是坏的**：预算只有 `BTN2_WRIST_MAX_ITER`(24) × 3.0 = **72° < 150°**
⇒ "输入端允许、求解器却到不了"这种自相矛盾的输入**真实存在**。

★ **2026-09-29 Task 7 用户裁决：走 (甲) —— 只把迭代上限 24 → 60，不做解耦。**
⇒ 单次调用里每个腕关节（J4/J5/J6）各自至多走 `60 × 3.0 = `**`180°`**
（乘积已按两个常数的**现值**核过）。**取 180 而不是 150**：入口那条
`ORIENT_MAX_OFFSET_DEG`(150°) **只夹倾斜分量**，**自转**分量（`rv[2]`）**不过它**，
而 `rotvec` 的最短弧上限**恒为 180°** ⇒ 入口能造出的最大目标是 **180°，不是 150°**
（50×3 = 150 只盖倾斜、盖不住自转）。**每轮仍是 3°** ⇒ "小步 ⇒ 偏向近解、不跳解支"
这条性质**逐字不变**。

⚠ **说准：这条改的是"转角意义上的对账"，不是"从此不会失败"。** 见下面那条零余量 ⚠ 的实测。

**失败模式（说准，别读成"夹到 180° 就停"）**：目标要的腕关节量超过这条预算 ⇒ 迭代跑满也到不了
⇒ **末尾那道「无条件自验」不过**（`|rotvec(targetR · FK_R(q)ᵀ)| ≥ Config::BTN2_WRIST_TOL_DEG`）
⇒ `button2SolveWrist` 返回 `false` ⇒ `button2OrientJointTarget` 把**六位全写回参照**
⇒ 纯函数这一层的**期望目标**就是**按下按钮2 那一刻的位姿** ⇒ 机械臂**保持 / 回到参照位姿**。

⚠★ **但"期望目标 = 参照"不等于"这一帧发出去的就是参照"**：纯函数的输出还要过**调用方**那一道
`clampJointStep`（定义在 `relay/Button2Joint.cpp`、声明在 `relay/Button2Joint.h`；
`RelayCore.cpp` 是它的**调用方**，逐帧步长限幅）—— 它把"本帧要走的量"逐关节夹到
`Config::ORIENT_MAX_STEP_DEG`（**3.0°/帧**）再累加到"上一帧**已下发**"上
⇒ **实际发出去的 `j` 是"朝参照收敛、每关节每帧 ≤ 3°"的那个值**，只有误差落到一步之内
（**收敛后**）才逐位等于参照。（这一道本来就在下一层，见上文
"`clampJointStep` 的逐轴限幅仍在下一层照旧（它只影响过渡帧，最终仍收敛到精确目标）"。）

- ⚠ **不是**"夹到 180° 那个中间角度就停在那里" —— 全函数**没有任何**"夹到上限就停下"的出路；
- ⚠ 也**不是**乱走（失败时纯函数六位逐位等于参照，是**一个**定义良好的位姿）；
- ⚠ 更**不是**"本帧不下发" —— 这条路上 `ServoJ(j)` **照样每帧发**，`j` 只是**朝参照收**
  （收敛后**逐位等于**参照）—— 与 `RelayCore.cpp` 里"死区把三轴全归 0 ⇒ **原地保持**，
  不是这一帧不下发"那条订正**同款**。

⚠★ **零余量 —— 而且这条有实测，不是我推的：180° 覆盖得了"转角"，覆盖不了"关节行程"。**
预算 `60 × 3 = 180` **恰等于**输入端上限 ⇒ **零余量**；腕三轴**不正交**
（`|z4·z6| = |cos J5|`）⇒ 同一个末端转角要的**关节量可以大于转角本身**。
**2026-09-29 Task 7 Step 7 探针实测**（扫描 `ref`：J1/J2/J3 ∈ {0, ±45} × J4/J5/J6 = −180..180
步长 30°；输入四种：`{150,0,0}` / `{0,150,0}` / `{0,0,180}` / `{−150,0,0}`；共 **237276** 个样本）：

### ★ 上游那条必须一起处理的（否则本方案被架空）

> ⛔ **【2026-09-29 晚 · 实施后订正】本批（Task 1–5）【未做】这一条。**
> 本批只实现了那个纯函数，**上游原样没动**：算偏移仍是**欧拉分量相减**、低通仍做在**欧拉域**
> （`Config::ORIENT_STYLUS_LPF_TAU_S`），合出来的 `m_btn2StylusFilt` **仍然就是喂给新函数
> 的第二个入参**（`curStylus`）。⇒ 笔杆 `Rz` 跨 ±180 时，喂进纯函数的依旧是一串
> "看起来平滑的假欧拉角" ⇒ **纯函数内刚获得的"跨接缝免疫"被架空，这条隐患【原样还在】。**
> **为什么不做**：它改的是 **`RelayCore.cpp` 的接线**（那块代码**不被任何测试编译**），与本批
> "实现一个**可测的纯函数**"是**两种风险**；混在一起做，出问题时说不清是哪一半。
> ⇒ **单开一批做**，判据：跨接缝时不应出现大幅关节位移。
> ⚠ 下面那句「决策（本方案采用）」里的"把低通与死区搬进旋转向量域"因此**作废为"未实施"**。

`RelayCore` 侧算偏移是**欧拉分量相减**（`RelayCore.cpp:1096-1098`），
**而且那道低通也做在欧拉域**（`ORIENT_STYLUS_LPF_TAU_S = 0.25`，`Config.h:1014-1016`），
喂进纯函数的是 `m_btn2StylusFilt[i] = m_orientRefStylus[i] + d[i]`（`RelayCore.cpp:1151-1153`）。
笔杆 `Rz` 跨 ±180 时（实测到过 −171°）偏移跳 ±360 ⇒ 低通把它**抹成 ~0.25 s 的斜坡** ⇒
`rpyToMatrix` 收到的是一串**看起来平滑的假欧拉角**。

**决策（本方案采用 —— ⛔ 但【本批未实施】，理由见上）**：**纯函数的入参改成"原始（未滤波）笔杆欧拉"**，
把**低通与死区搬进纯函数的旋转向量域**（那里没有接缝）。

- 理由：① 新公式吃的是 `rpyToMatrix(欧拉)`，上游在欧拉域做的任何线性操作都会破坏它；
  ② 搬进去以后它们**有单测**（今天没有）；③ `RelayCore.cpp:1182-1183` 那条"不搬进去"
  的现行理由（"会改掉已被现场验证过的语义"）针对的是**正在被替换掉的欧拉偏移管线**。
- 代价：**改的是没有测试的接线**（`RelayCore.cpp` 不被任何测试编译）⇒ 只能复审 + 上机。
- `m_btn2StylusFilt` **保持不动**（旧 RPY 路径与诊断还在用），只是不再喂给关节路径。
