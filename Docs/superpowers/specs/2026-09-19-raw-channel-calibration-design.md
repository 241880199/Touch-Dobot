## 1. 为什么要重做

现有求解链路**预设了六件东西**，其中三件今天被实机数据证伪：

| 预设 | 位置 | 今天怎么暴露的 |
|---|---|---|
| 重力**转置**约定 | 模型形式 | 解出 0.654 vs 真值 0.659；**残差只从 0.045 涨到 0.68，报不出错** |
| **ψ = 纯偏航**（旋转只 1 个自由度） | 模型形式 | 真值需要 z 反射 → 模型只好**翻质量**（`dm = −0.417`，被非物理门限拒） |
| **ψ 是常数** | 参数 | 90° → 扫出 79/80.5/81.5 → 又 −99.5 → 又 +29.5 |
| **z 符号** | 边界手工对齐 | 又是预设，只是换了个地方放 |
| **力/力矩参考点** | 模型形式 | 从未验证 |
| **两通道等权** | 目标函数 | `ssF/ssM ≈ 1900`，力矩那票等于没有 |

**机理（本项目栽过三次的同一个根）:** 最小二乘把模型表达不了的部分**摊到其他自由参数上**。
**「残差小」不能证明「参数对」** —— 本批数据上形式错 **0.018 N**，而质量符号翻了。

## 2. 物理关系（不是猜测，是力学）

传感器测的是**它自己原点处**的力旋量。重力在法兰系为 `g_i = R_iᵀ(0,0,9.81)`。

```
F_i = b_F + A · g_i           A: 3×3 —— 传感器测量系相对法兰系的响应，【完全自由】
M_i = b_M + c_s × (A · g_i)   c_s: 质心（传感器测量系）
```

- `A` **不假设**是偏航、**不假设**是旋转、**不假设**手系 —— 9 个元素全部由数据定
- 力矩不是独立的 3×3：它是 `c_s × F`（叉乘结构），所以给定 `A` 后力矩只多 3 个未知量
- `c_s × b_F` 是常量，被 `b_M` 吸收 —— 所以上面这条是完整的

**未知量: `A`(9) + `b_F`(3) + `c_s`(3) + `b_M`(3) = 18。** 姿态数 n 给 6n 个方程。
n=6 → 36，够。**全部线性**（`A` 线性、`b_F` 线性；`c_s` 在给定 `A` 后也线性）→
**不需要任何扫描**。

> **与现行算法的区别**: 现行是"扫描 ψ 找最优角"，这里是"解一个线性方程组"。
> 现行是"假设旋转轴是 z"，这里是"数据填满 9 个元素之后我们再看它是什么"。

## 3. 从 `A` 读回物理量（这一步是"标定"，不是"猜"）

```
m      = (σ₁σ₂σ₃)^(1/3)            ← 质量尺度（σᵢ 为 A 的奇异值）
parity = sign(det A)                ← 手系，【由数据给出】
S      = diag(1, 1, parity)
Q      = S · A / m                  ← 对【任意可逆 A】都满足恒等式 A = m · S · Q
```

> **⚠ 2026-09-19 规格更正。** 原文写的是 `Q = U·diag(1,1,parity)·Vᵀ` —— **错的**：
> 当 `σ₁=σ₂=σ₃`（安装正常的好情况）时 `U`、`V` 不唯一，该式非唯一确定；
> 且非各向同性时 `m·S·Q_spec = A` 要求一个正交阵等于 `diag(σᵢ/m)`，不可能。
> 已改为上面的 `Q = S·A/m`（实现者提出并经评审独立验证）。**Task 9 的换算依赖这一版。**

**自检（必须做，且必须能拒绝）:**

| 检查 | 判据 | 不通过时 |
|---|---|---|
| **模型形式（失拟检验）** | 自由拟合 `F=b+M·g`(12参) 与参数模型 `F=b+m·S·R·g`(4参) 的 **F 比** | **报「模型形式不匹配」并拒绝给出参数** |
| 参数不确定度 | `(JᵀJ)⁻¹` 对角开方 | **随结果一起打印**，让"±0.05"和"±0.5"可区分 |
| 各向同性比 | **报告量**，带不确定度 | **不作门限** —— 真实响应的非正交是**物理属性**，不是罪证 |
| 逐姿态残差 | 每个姿态的 rms | 标出坏姿态 |

> **⚠ 2026-09-19 规格更正（评审发现）。** 原文把各向同性比当门限，且容差取自
> `paramSigma` ← **拟合残差**。这是个自指的陷阱：**模型形式错 → 残差涨 → σ 涨 →
> 门限放松得比 iso 涨得更快**。评审者跑出反例: 用历史上的**转置回归量**生成数据,
> 拟合 `iso=2.01` 而门限 `2.59` → **错误模型被接受**, `m=0.4159`（真值 0.42）。
> 反方向同样坏: 真实 `A` 本就 6.5% 非正交（物理属性），无噪声重放下 `iso=1.06548`
> vs 门限 `1.00000` → **正确答案被拒**。
>
> **改用失拟检验**: 它直接问"约束形式能否与自由形式解释得一样好" ——
> 判据来自分布而非拍定的数，且**不依赖残差自估的噪声**。

**这四条是本次重做的核心价值** —— 现行算法只输出一个标量残差，
而**标量残差对"模型形式错"是不敏感的**。

## 4. 数据流

```
@1304 SixForceValue (原始)  ──►  本地线性解 (A, b_F, c_s, b_M)
                                      │
                                      ├─► m, Q, parity, c_flange     ← 【本地补偿用】
                                      │     运行时: compensated = F_1304 − b_F − A·g
                                      │
                                      └─► (m, c_flange)  ──►  发给机械臂 EnableRobot
                                                                 │
                                                                 └─► 【闭环验证】
```

**`c_flange` 由 `c_s` 经 `Q` 换到法兰系**（`c_flange = Q⁻¹·c_s`，手系按 `parity` 处理）。
注意 `Q⁻¹ = Qᵀ` 仅当 `Q` 正交 —— 由各向同性检查保证。

## 5. 闭环验证（用户明确要求的对比）

**发出去之后，机械臂把它的负载模型换成正确的，于是它加工出来的 `@576` 的
【姿态相关部分应该塌掉】。** 这正是"对比本地处理后的数据与机械臂得到新参数后加工得到的数据"：

| 观察 | 含义 |
|---|---|
| `@576` 的 `M` 尺度塌到 ≈0（姿态无关） | ✅ 我们的参数对，且机械臂**确实采纳了** |
| `@576` 仍有明显姿态相关 | ❌ 三者之一：参数错 / 符号约定不符 / 机械臂没采纳 |
| 本地 `compensated` 在所有姿态 ≈0 | ✅ 本地模型自洽（由拟合保证） |

**这条验证把三个未知一次分开**：参数正确性、`EnableRobot` 的符号约定、机械臂的采纳行为。
**不需要额外假设。**

> 进一步: `@576` 应当 ≈ `@1304` 经 `A` 与常量变换后的结果。
> 若两者对不上，就说明机械臂的加工规则不是我们以为的那样 —— 那也是**测出来的**，不是猜的。

## 6b. 发给机械臂的参数（用户 2026-09-19 定：三条一起用，传全）

**只有一条指令能传质心** —— 厂家文档（TCP/IP 接口文档 P7-8、P19-20）:

| 指令 | 能传什么 | 不能传什么 |
|---|---|---|
| `EnableRobot(load, centerX, centerY, centerZ)` | 质量 + **质心**（±500 mm） | 惯量 |
| `PayLoad(weight, inertia)` （别名 `LoadSet`，六轴独有） | 质量 + **惯量**（kg·m²，单标量） | **质心** |
| `LoadSwitch(status)` | **负载设置开关**（默认**关闭**）；"开启后可提高碰撞检测灵敏度" | — |

**所以三条各补一块，缺一不可：**

```
EnableRobot(m_full, cx, cy, cz)     ← 质量 + 质心（唯一通道）
PayLoad(m_full, I)                  ← 惯量（EnableRobot 传不了）
LoadSwitch(1)                       ← 打开负载设置，否则碰撞检测拿不到它
```

### 为什么"质心只在本地补偿"不够（用户提问引出，控制器查证）

**文档证据:**
- CR 手册「末端负载曲线」把负载规格定义为 **`(m, r=√(X²+Y²), Z)` 三元组**，
  质心 Z 是判断"工况是否超限"的必需输入。
- `LoadSwitch` 的描述把**负载设置与碰撞检测灵敏度直接绑定** —— 机械臂用负载模型判断碰撞。
- `EnableRobot` 的签名本身就带三个偏心参数（±500 mm）—— 厂家预期用户会填。

**后果对照:**

| | 质心只在本地补 |
|---|---|
| ✅ 我们的力/力矩读数 | 完全正确（触觉/力反馈要的就是这个） |
| ❌ 机械臂的碰撞检测 | 力矩预测缺重力**力矩**项 → 误触发/漏触发；且我们代码还发 `LoadSwitch(0)`，等于**主动放弃**这个安全能力 |
| ❌ 拖拽示教 | 拖拽要补重力力矩 → 手感错、甚至失控 |
| ❌ 工况判断 | 按 `(m, r, Z)` 判超限 → 没有 Z 判不准 |
| ⚠️ 安全 | **1.5 kg 那次突动就是重力力矩补偿被改变**；CoM 是那个力矩项的核心 |

### ⚠️ 现在的代码把质心**设过**了，换成 `Payload` 会把它丢掉

`enableRobotWithPayload()` 每次连接发 `EnableRobot(m, cx, cy, cz)` ——
**质心是设了的**。所以不是"要不要加"，是"**不要退化成只发质量**"。

### 惯量：**目前只有估算，而估算与"不猜"的原则冲突**（2026-09-19 更正）

`PayLoad` 的 `inertia` 是**单一标量 kg·m²**，文档**没有定义是哪个分量**。

> **⛔ 原文这里写的是「惯量张量可以从几何算出来…这是从物理模型算的，不是猜」—— 已被推翻。**
> 用户质疑得对：**从形状模型算惯量，本质就是对形状做假设** —— 和 ψ 是同一类东西，
> 只是藏得更深：它不显式地问"选哪个角"，而是**把假设默默吃进数字里，然后看起来像个精确值**。

**`Hardware/tools/compute_payload.py` 的估值上有三处【各自独立】的形状假设，每处都能动 10~35%:**

| 假设 | 对 `Izz` 的影响 | 来源 |
|---|---|---|
| 两根导杆是否按真实半径 31 mm 建模 | **35%** | 该偏置占其 `Izz` 的 99.2% |
| 紧固件的**径向偏置** | **+7~10%** | 现行代码把它们放在轴线上（`m·r²` 项缺失）；实际 M6 在 `BC_D=50` 分度圆（r=25）、销在 `DOWEL_R=25`、耳座侧在 `ROD_R=31` |
| 传感器按**实心圆柱**还是**薄壁圆环** | **+34%** | 而且 §6b 下面那条未决（`c_s` 54.55 vs 解析 130.3 mm）**已经说明传感器内部质量分布不是均匀的** —— 与这条假设同源 |

**每一个新发现的几何细节都会让这个数再动一次。这不是"有误差的测量"，这是猜的特征** ——
测量不会因为你想起了某个零件是环形的就变 34%。

**因此：**

1. **在惯量被实测之前，不得把它当作可信参数下发给机械臂。**
   `compute_payload.py` 的输出标记为**参考量（estimate）**，不是标定结果。
2. **惯量是可实测的**，三条路（待用户定）：
   - **① 动态辨识**：让机械臂按**已知轨迹**运动（小幅度、低速度、设计好的动作），
     传感器测到工具惯性产生的力旋量 → 反解惯量张量。**测的是真实装配状态**，但机械臂要动。
   - **② 台面摆测**：把工具链拆下悬挂摆动，**周期给出绕支点的惯量**，平行轴换回质心。
     **完全不碰机械臂**，与"称重"同性质；代价是拆装 + 需换几个轴向才能凑齐张量。
   - **③ 先发一个算出来的值** —— **与"任何猜测都不可取"冲突，不作推荐。**
3. `PayLoad` 要哪个分量仍未定义 → 脚本打印 7 个候选**不猜**，留待实机用 `P→0` 定。

## 6c. 惯量的动态辨识（**用户 2026-09-19 选定**）

> **用户决定**: 选择**动态辨识**，理由是**台面摆测缺少精密计时设备**（摆动周期只能目测，
> 误差直接进结果）。这是一条硬约束，不是偏好。

### 原理

工具链刚性固定在传感器下方。机械臂运动时，传感器测到的是**工具链惯性产生的力旋量**叠加在重力上。

设传感器原点为 O，`r_c` 为质心相对 O 的位置，`I_O` 为绕 O 的惯量张量，`ω`/`α` 为传感器系的
角速度/角加速度，`a_O` 为 O 点的线加速度：

```
F = m·(a_O + α × r_c + ω × (ω × r_c))          （传感器系，含 −m·g 项，静态标定已分离）
M_O = I_O·α + ω × (I_O·ω) + m·r_c × a_O
```

**关键简化：`m` 与 `r_c` 已经由静态标定【实测】得到**（`A`、`c_s`、`b_F` 同源）。
所以动态辨识只需解 **`I_O` 的 6 个独立分量** —— 未知量少、条件更好。

> ⚠ `I_O` 是**绕传感器测量原点**的，不是绕质心。发给机械臂要的是绕**法兰面**的 ——
> 用平行轴换两次（O→质心→法兰面），两次平移都必须显式写出并测一下（今天已经因为
> 平移项漏一次而少算 10%）。

### 微分问题的处理（**本设计最容易出错的地方**）

`M_O` 需要 `α` 与 `ω`。**不要对噪声数据做数值二阶微分** —— 高频噪声被 `d²/dt²` 放大平方倍。

现行代码里位姿来自 **10 Hz** 的仪表盘查询（`POSE_QUERY_INTERVAL`），**这个速率根本不够**。
可用的是 30004 帧里的 **125 Hz** 通道，而且**已经验证过**：

| 字段 | 位置 | 用途 |
|---|---|---|
| `ToolVectorActual` | @624 | TCP 笛卡尔实际坐标（**已验证是基座系**，见 §6）|
| `TCPSpeedActual` | @672 | TCP 笛卡尔实际速度（**已验证是真实读数**）|
| `QDActual` | @480 | 实际关节速度 |
| `ActualQuaternion` | @1384 | 实际四元数（姿态更稳）|

**做法**: 采集 `ToolVectorActual` 的 125 Hz 序列，**拟合一条平滑轨迹模型**（如正弦 + 谐波），
再对**拟合出来的模型**解析求导得到 `ω`/`α`。这样微分作用在已去噪的解析函数上，不是作用在原始数据上。

**独立验证**: `TCPSpeedActual` 是机器人自己给的速度 —— 与对位置拟合求导的结果应当一致。
**两者对上，才说明微分是对的**（这是免费的自检，且不是同一个来源）。

### 激励设计（决定能不能解出来）

**信号量级** —— 传感器看到的惯性力矩是 `I·α`，而 `α = θ₀·ω²`（正弦往复）：

| 幅度 | 周期 | α (rad/s²) | 惯性力矩 (N·m) | 对比静态模型误差 0.0014 N·m |
|---|---|---|---|---|
| ±10° | 2.0 s | 1.7 | **0.015** | **10×** |
| ±20° | 1.5 s | 6.1 | **0.052** | **37×** |
| ±20° | 2.0 s | 3.5 | **0.029** | **21×** |

> **用户 2026-09-19 澄清: "运动速度慢是出于安全性考虑，在运动范围较小的情况下可以采用正常速度"。**
> 所以**不要人为放慢** —— 角加速度 ∝ 幅度 × 速度²，放慢会平方地杀死信号。
> 由**小范围**保证安全，由**正常速度**保证可测。原先为救慢速信号而引入的同步检波
> **不再是必需**（保留它作为进一步提 SNR 的手段，但方案不依赖它）。

**用【腕关节】激励，不做平移。** 理由:
- **平移只能测出 `m` 与 `r_c`** —— 那两个已经从静态标定【实测】得到，再测一遍没有信息
- 要测 `I` 必须**转动**
- **腕转时臂身几乎不动**，只有末端姿态变 —— 干涉风险最小

**幅度与范围** —— 必须在【已经安全走过的信封】之内（由 `calib_poses.txt` 的实测坐标推出）:

```
x: -231.1 ~ -13.5 mm      y: -125.1 ~ +71.6 mm      z: +441.5 ~ +575.6 mm
中心 ≈ (-110.7, -58.6, +497.1) mm
```

腕转 ±20° → 笔尖行程约 **87 mm**，只占该信封的一小部分。

**轴数与条件数** —— `I_O` 有 6 个独立分量，**单一轴的往复不足以保证可辨识**
（`ω × (I_O·ω)` 是二次项，需要不同轴把分量分开）:
- 建议 **2~3 个不同旋转轴**各一组
- **必须报条件数；条件数过大就拒绝给结果**（同 Task 1 原则: 激发不足时不给数，
  而不是给一个看似合理的数）
- **组数与周期数由条件数决定，不拍死**

#### 收口：物理测量拿不到 ⇒ 改走**数据路线**（用户 2026-09-19 明示无法称重/量厚）

**先证一条否命题：纯载荷数据【定不出】测量原点 —— 这是可识别性问题，不是数据量问题。**
传感器的每个读数都是相对它自己的测量原点；**一个薄的和一个厚的传感器，对同一个负载会给出
逐位相同的六维读数**。所以任何采集都定位不了原点，多采也没用。转接法兰同理。**必须有外部参照。**

**外部参照就在 30004 帧里 —— 机械臂自己报的负载，而且就在它自己的法兰系：**

```

| CenterX/Y/Z | @1176 | 负载偏心距离 (mm) |
```

（`RelayCore.cpp:99-107` 已在读，只打印。）实测记录：
`机械臂自报 load = 0.404 kg  center = (0.3, -0.1, 68.7) mm`，**回读与下发分毫不差** ⇒ 它确实采纳了。

```

ψ 时代用机械臂自报基线独立解出 comZ = +66.3 mm  ⇒  d = 11.75 mm      (progress.md:603)
⇒ d ∈ [11.75, 14.15] mm —— 落在传感器内部 (0~31.5) 且靠近中位 (15.75)  ✓
```

> ⚠ **保留**：那个 68.7 是**我们自己**早先（ψ 时代 + CAD 种子 80.4）下发进去的，不是独立第三方。
> 所以这是一次**一致性检验**，不是证明 —— 它把 `d` 收进一个物理上合理的小区间，仅此而已。

**那个"和"有一个值就够了。**

#### ✅ 判据（写死，不许放宽）

**任何候选 `cz` 必须让 `d = cz − c_s` 落在 `(0, 31.5) mm` 内。落在外面 ⇒ 哪里错了，不得下发。**

⚠ **两个"质量"不是一回事，别混**：机械臂的 `load` = 挂在它法兰上的**全部**（转接法兰 + 传感器

### 8b. **第 2 步的具体操作（2026-09-19 修订 —— 必须含重复姿态）**

```
1. 启动客户端，机械臂连接
2. 'm' 进入采集
3. 摆 6~8 个姿态（务必含【笔接近水平】与【朝上】的姿态，跨度 ≥30°）
   每个姿态按 SPACE 采 1 秒
4. ★ 重复对（模型形式检验的尺子）—— 在【当前这个姿态上】原地采：
      摆姿态 → SPACE 采样
      保持不动 → 按 'r' → 再按 SPACE 采一次（同一姿态）
   两次采样之间机械臂【不许移动】。建议 2~3 对（换个姿态再来一遍）。
5. 's'
```

> **⚠️ 没有第 4 步，`'s'` 会拒绝**, 报 `MODEL_FORM_NO_REPEAT`。
> **那是门在正确工作, 不是故障** —— 模型形式检验需要一把"姿态间可复现性"的尺子,
> 而它只能从重复姿态量出来（规格 §3）。

**为什么是原地复采，而不是"回到第 1 个姿态再采一次"（旧写法，已废）**：

- 姿态是**手拖**出来的，拖不出两次一样的位姿 —— 旧协议在实机上**根本执行不了**。
- 而它坏在**危险的那一侧**：一对的两次访问落在**不同位姿**上时，差值里混进两个位姿之间的
  重力差（零点几 N，对着 **0.0224 N** 的残差），`σ_rep` 被抬到 ~0.5 N，`χ²/dof` 落到
  ~0.002，门限随之放宽到**无条件放行** —— 一把永远通过的尺子，正是本轮要消灭的
  "绿色但不携带信息"。
- 原地复采与"拖不回去"无关。但**"保持不动"不等于"位姿完全不变"** —— 依据是量出来的，不是
  断言出来的：实机日志 `Touch_Client/force_demo_log.csv`（8285 行，含位姿列）里，
  **8284 个相邻帧中 8113 个逐位相同，另有 63 个带小幅非零步进**；按 0.5 deg/mm 容差归并出
  **7 段保持不动**，其中 **6 段**相对各自起点偏了 **0.007~0.199°**（位置抖到 0.47 mm，而
  **位置不进模型** —— 回归量只有 `rx/ry/rz`）。
- 这点抖动量级多大：最坏一档 `m·g·sin(0.199°) ≈ 0.014 N`，约 **0.65×** 那个 **0.0224 N**
  的残差（典型的保持段 ≤0.0007 N）。而且**同一份姿态抖动也会进入拟合残差** —— 所以原地复采
  作为一把尺子仍然成立（这一点比原来那句"0 段漂移"更站得住），只是它量的是
  **"含一点姿态抖动在内的一切"**，不是"除姿态变化之外的一切"。
- **操作员该比的是两个【打出来的数】，不是任何隐含门限**：采样当场打印的每对 `σ_rep`，与
  `'s'` 屏幕上的 `rmsF`（`fit.rmsForceN`）—— 两者同量级才说明这一对干净。**不要**拿"零点几 N"
  当尺子：0.2° 的抖动只花掉 0.65× 残差，任何"零点几 N"的报警都会放它过去。

> **⊙ 本节是"原地复采为什么成立"的唯一权威出处。** `Touch_Client/main.cpp` 与
> `Touch_Client/force/RepeatPairRegistry.h` 只引用本节（一行），不再各自复述理由 ——
> 这段论证此前散在三处，已经漂移过一次（"0 段发生姿态漂移"这个断言与日志不符）。

`'r'` 配的是**上一次采样**，即一对 = `(count−1, count)`；**还没有任何采样时按 `'r'` 会被
明确拒绝**，且不登记任何一对（`RepeatPairRegistry::NO_PREVIOUS`）。

**为什么要 2~3 对**: 尺子的自由度 = 重复对数 —— **前提是每一对取自【不同】姿态**。
在同一个姿态上连着配对会让相邻两对共用一次采样，`d²` 之间相关 1/4，真实自由度掉到约
`2R/3`（`2R²/(3R−1)`），而控制台按 `R` 报。方向是**保守**的（门限随 `R` 收紧），不是安全问题。

实测假拒率（模型正确时被误拒；`α = 0.9999`、`r = 3`，出厂外蒙特卡洛每点 4 万次 ——
表见 `Touch_Client/force/PayloadCalibration.cpp` 里 `RAW_MODEL_FORM_ALPHA` 的说明）:
**R=1 → 2.06%, R=2 → 0.27%, R=3 → 0.05%, R=4 → 0.02%**。
（**12% / 4.9% / 2.5% 是放宽前 `α = 0.997` 那一列，勿再引用**：用户 2026-09-19 已批准
`RAW_MODEL_FORM_ALPHA = 0.9999`。）错误模型的拒绝余量仍有 **26~400 倍**。
