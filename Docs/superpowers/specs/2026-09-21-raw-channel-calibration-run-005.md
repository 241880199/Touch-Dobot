## 7. ★★ 悬案：`@720` 在真实载荷下与传感器差 25~34 倍

### (d) ★★★ 模型：为什么**不拒**、力又去哪了


## 12. 帧解析审计（本趟新做，回答"会不会读错/错位"）

**结论分两半，结论相反：**

### 12.1 字节流错位 —— **不会**，靠"宁断不错"

`RobotConnection.cpp` 的 `robotRecvRealtime`：

```cpp
int n = recv(sock, buf, len, 0);   // len = 1440
if (n == len) return true;          // 只认【恰好一整帧】
if (n <= 0)   { closesocket(); }
return false;                       // 其余一律 false
```

调用方（`RelayCore.cpp` 的 `forceReaderThread`）收到 false 就 `break` ⇒ **外层重连**。
- **部分读取**（`n < 1440`，TCP 完全允许）⇒ 重连
- **粘包**不会给 `n > 1440`（`recv` 的 `len` 是上限，多余留内核缓冲区）
⇒ **只有"恰好一整帧"才被接受 ⇒ 读取位置永远落在帧边界上。**

**⚠ 三条要记的：**
1. 代价是**会频繁重连**，每次重连丢 2 s（`FORCE_RECONNECT_INTERVAL = 2000` > `FORCE_STALE_MS = 200`）
2. **★ `raw`/`tcpForce`/`sixForceRaw` 在帧陈旧时【不会被置零】**（只有 `compensated`/`filtered`/`hapticOut` 被置零）
   ⇒ **掉线期间打出来的 `@576/@720/@1304` 是【上一帧的冻结值】，不是零。**
   守卫在的：夹具采样会作废那一笔（`[BIAS] 采样超时`）、闸门可用性判据含 `!fd.isStale` ✓
3. 它依赖一个**未验证的假设**：机器人对新 TCP 连接**从帧边界开始发**。文档没写。

   两条互斥出路：**降噪**（把 0.17 N 压下去 —— 即上面第 6 条那个惯量项）或**给演示单独放宽死区**
   （代价是噪声穿过来）。**⇒ 这可能才是"毛笔细微力能不能感觉到"的真正决定项。**
8. **★★ 闸门的出路 —— 它的判据前提已被两次独立测量推翻（§7.5 末）**
   两个候选通道**都不可能**同时满足"随配置负载走"与"如实反映工具端外力"。⇒ **不能再"比"了。**
   四条出路（**这是设计决策，要用户定**）：
   - **(i) 把"不一致"那一条降级为【只报不判】**，只保留 `UNCALIBRATED` / `REFERENCE_UNAVAILABLE`
     两条配置态守卫。**这与它最初的样子一致**（`g_guardEmaDiag` 本来就是只报不判），
     而且**这是让演示能跑起来的最小改动** —— 有接触力时不再掐断触觉。
   - **(ii) 换一个可达的目的**：不"与机械臂比"，改判**自身一致性**（如逐姿态零偏是否一致）。
     ⚠ 有自指风险（判据的量不能来自它自己要检验的量 —— 本项目记过四次账）。
   - **(iii) 只留配置态守卫**，把"一致性"整条删掉。
   - **(iv) 另找独立参照**：定期用**已知质量**（砝码/水）核对 —— 那是**计量**，不是运行时闸门。
   **⚠ 不要靠改容差压过去**（理由代码里已写明：容差由实测导出）。

### ★ 建议的推进顺序（不是并列）
